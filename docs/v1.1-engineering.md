# v1.1 engineering and reproduction

The static product gains `/players/` and `/nl/players/`. One derived index contains identity/context, nominal reliable minutes and separate common/similarity/translation/DNA flags. Provider-native details are loaded only on opening a profile; up to ten same-provider, competition-season, broad-role neighbours use `common-similarity-v1`. Cross-provider manual comparison uses the three common v1 dimensions; native metrics are comparable only inside the same provider. Unknown values stay null. URLs preserve search, filters, pagination, selected profile and comparison; identities, never names, form the keys. Results render 50 rows per page. No thousands of thin SEO routes or hosted search service are created.

## Offline product checks

```sh
make setup
make test
make release-build
make release-validate
make smoke
```

These commands use synthetic fixtures and committed derived data. They never fetch full event datasets. Python 3.12/3.13, Node 24.19.0 and the existing lockfiles remain supported. The additive Pydantic contracts generate `profile-contracts.ts` and `artifacts/v11/contracts.schema.json`; original contracts/OpenAPI and all 2,146 scientific-lock entries are unchanged.

## Full data build

```sh
# Uses the reviewed/pinned source audit, verifies cache and all full partitions.
make v11-data-build
# Isolated small development output; never publishes or changes the full cohort.
uv run fri data expand --max-matches 5
```

Full stages: pinned catalogue/source audit → hash-verified download → canonical event/observation Parquet → conservative minutes → native/common aggregation → temporal/provider evaluation → strict public export. The initial online audit was run before ingestion using `scripts/v11_audit_sources.py`; rerunning that script explicitly discovers current upstream metadata and must be reviewed before accepting a new revision. Ordinary reproduction does not silently advance the pinned revision.

The ~4.78 GB source cache includes all catalogue lineups and the selected event feeds. Downloads use upstream MD5 plus SHA256, bounded HTTP streams and validated Range resumption where supported. Every reuse is checksummed. Wyscout's zipped JSON arrays stream one match at a time. Parquet stores 11 substantial provider/competition/season partitions, not thousands of tiny event files. DuckDB views expose observations, player-season profiles, provider-native features, common features and eligibility. Extraction keys include code, pinned sources and selected match IDs; hash-mismatched or incomplete partitions rebuild. Separate `development-5` output cannot overwrite `full` or production JSON.

Each profile records source revision/files, source/feature manifest hashes, exact code commit and pipeline hash. `build-manifest.json` payload file/byte totals exclude the manifest itself to avoid self-reference; the publication inventory and release manifest include it. Source ZIP member names are explicit. Provider identities remain separate, and memberships come from observed matches, not current-team metadata. No birth/passport fields are published.

## Publication and size budgets

`config/v11-public-artifacts.json` is a separate strict allowlist joined with the original inventory at build time. Every file is schema/hash/byte validated, and unknown files in either public artifact tree fail the build. Raw event records, arbitrary additional fields, Parquet, DuckDB, posterior arrays, archives and secrets are excluded. Profile detail schemas fix native fields per provider; the common schema admits exactly three fields. Browser responses verify hashes against the release-pinned integrity index before becoming typed objects.

Detail files are sharded by the last two digits of the provider ID so integrity manifests remain comfortably below the 200 KB fetch bound. No compression-dependent size bypass exists: every JSON response also has a 3 MB decoded bound. Search index <1 MB gzip; each profile <50 KB. The 3,074-profile build adds about 11.15 MB derived JSON. The explicit total JSON budget is now **55 MB** (was 40 MB); the static export budget is **65 MB** (was 50 MB), accommodating the measured ~57 MB release and existing frozen evidence. These are maximums, not targets.

Measured local performance and environment are recorded in `artifacts/v11/performance.json`; reproduce using `node apps/web/scripts/players-performance.mjs` against the production preview. This checks the actual full index in EN/NL at 375 and 1440 px, ensures no detail requests on first load, records filter/render and profile-fetch timings and saves screenshots. Node/Python gzip levels differ slightly; both measures stay far below the budget. Localhost timing is not a claim about slow devices or real internet/CDN latency.

## Operations, branding and cost

The existing Render static service continues to track protected main with `checksPass`. `/players*`, favicon and brand responses use explicit revalidation; existing security headers, same-origin integrity and static 404 behaviour remain. Production headers are synchronized through the existing authenticated Render API because the service is not automatically Blueprint-managed. No service, worker, database, disk, domain or subscription is added. Incremental fixed infrastructure cost: **$0**; normal existing build/bandwidth usage can change. Frenkkester.com is untouched.

The supplied horizontal, compact, reversed and favicon assets from the Phase 5 follow-up are included in this release. The desktop header uses the horizontal mark, mobile uses the compact mark, the reversed artwork is used for dark-background sharing, and metadata declares favicon/browser/apple icons. Brand source PNGs remain byte-identical. Both locales and responsive states are checked in all three browsers.

Release order: PR → required CI → merge main → main CI → Render checks-pass deployment → production manifest/routes/data/header verification → annotated v1.1.0 tag on exactly that main commit → GitHub release. The v1.0.0 tag is immutable. Exact deployment/merge/tag identity is recorded in the GitHub release evidence; the deployed manifest is the authoritative application SHA.
