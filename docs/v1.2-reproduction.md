# v1.2 reproduction and operations

This release adds data and independently versioned methods. All existing scientific JSON, v1.1 profiles, schemas, plans, source pins and old WSL scenario encodings remain intact. Normal frontend build and CI read only committed, licensed derived artifacts: no full event download, training job, database, API or paid service is required.

## Full source build

Use Python 3.12/3.13 with `uv sync --frozen`, Node from `.node-version` and `npm ci` in `apps/web`.

1. The fresh audit was committed as `ae3badb`, before evaluation. `make v12-audit` performs **new discovery** and should be reviewed as a deliberate source update; do not refresh pins merely to reproduce this release.
2. Reproduce/restore the pinned v1.1 cache using `make v11-data-build` as documented in `docs/v1.1-engineering.md` (or retain the existing verified `data/processed/v11/full` partitions). v1.2 checks each reused Parquet partition against its original manifest before richer extraction. Never publish a changed v1.1 output over the frozen release.
3. `make v12-fetch` retrieves exactly the committed `config/v12-sources.json` allowlist. A clean cache needs network; subsequent retrieval verifies SHA-256 and is offline. Fresh builds do not consult a moving repository tree. The extra pinned cache is 3,696 files / 4,710,560,416 bytes, separate from the reused v1.1 Wyscout cache.
4. `make v12-data-build v12-recruitment-build v12-evaluate v12-public v12-reports` parses metadata and new StatsBomb scopes, extracts rich Wyscout observations, evaluates the registered threshold grid, validates/shards permitted derived outputs and regenerates exact reports. Metadata/physical inputs are hash-checked too. The public stage is validated completely before replacing the previous publication. Run serially: evaluation follows extraction; publication follows evaluation.
5. `make test release-build release-validate`, then `cd apps/web && npm run test:smoke`. Integration tests verify the entire additive allowlist/schemas/hashes and generated contracts without raw caches. They require all 85 capability decisions (80 StatsBomb catalogue scopes + five Wyscout scopes).

Raw events, lineup feeds, source archives, full tracking, Parquet caches and candidate identity joins are not frontend assets. Full caches are intentionally ignored by Git. Full source rebuild output includes the build's Git code commit and pipeline hash; changing code commit alters provenance bytes, while equal source/code revisions reproduce the derived bytes.

## Identity and scope policy

Provider IDs and player-season profiles are distinct. No cross-provider person merge occurs. OpenFootball unique name+DOB+recorded country matches create external metadata candidates only. Club links require an exact normalized alias and country with one candidate; unresolved names and ambiguous aliases remain distinct source entities. Country-folder spelling aliases (Latvija/Latvia, Macedonia/North Macedonia, Bosnia variants) are explicit. Reserve-team `ii)` markup is removed; it never merges a reserve squad with its senior team. Fixture status annotations remain match metadata, not club names. Source dates stay verbatim; fixture snapshots do not imply current squad membership.

StatsBomb domestic completeness is catalogue/schedule coverage, not a claim that all player minutes survive conservative parsing. Extra-time/participation conflicts withhold affected player-seasons. Cup and international observations remain separate. New recruitment gates are league/role specific; no failed scope acquires the capability merely by being searchable.

## Publication and performance budgets

The old 65 MB total export allowance covered the earlier dataset. Preserving its bytes while adding 25,885 metadata records, lazy fixtures and new profiles requires an additive storage allowance. v1.2 permits **100 MB derived JSON / 115 MB total static export**, with the unchanged **3 MB maximum per artifact**. These are storage ceilings, not initial downloads. Individual club details and integrity manifests are sharded; metadata and specialist records load only on demand. The performance index remains approximately 142 KB gzip and contains no vectors. Each recruitment league loads independently; the other four load only when wider discovery is enabled.

Cold mobile measurements use the existing 4× CPU / 1.6 Mbps / 150 ms / three-run procedure. LCP <2.5s, CLS <0.1, blocking <300ms, initial JS gzip ≤250KB and transfer ≤750KB remain the targets. Decoded data budgets are 3MB for the expanded player index, 1.5MB for a native recruitment league and the prior 350KB for other measured routes. Pure player filters must remain <100ms. Report actual results rather than equating total hosted data with page payload. No backend is justified by this dataset size.

## Deployment and rollback

Keep the existing free Render static site, `main`, build command and checked-CI deploy trigger. No new infrastructure or cost. Merge only after all CI jobs pass, verify exact main SHA against Render and `/release-manifest.json`, test EN/NL workflows live, then create `v1.2.0` without moving `v1.1.0` or prior tags. Rollback uses the previous successful Render deployment; retain old source/artifact versions. See the existing release checklist for route/header/hash verification and credential handling.
